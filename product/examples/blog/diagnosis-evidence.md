## 같은 상태 이름, 다른 원인

Pod가 이미지를 가져오지 못한다는 메시지는 출발점입니다. 이미지 이름이 잘못됐을 수도 있고, 레지스트리 인증이나 네트워크 접근이 막혔을 수도 있습니다. 하나의 상태 이름을 곧바로 특정 수정 명령에 연결하면 다른 문제에 같은 처방을 적용하게 됩니다.

여기서는 진단 도구의 예시를 통해 관측과 판단을 분리합니다. 실제 클러스터에서 수집한 사건 기록이나 운영 결과를 제시하는 글은 아닙니다.

## 증거가 먼저 도착하는 파이프라인

먼저 Pod 명세와 이벤트를 읽고, 관측 시간과 대상 식별자를 함께 기록합니다. 그다음 가능한 원인을 나열하고 각 원인을 뒷받침하거나 반박하는 항목을 붙입니다. 수정안은 이 기록을 읽는 별도 단계에서 만듭니다.

```text
대상 확인 → 읽기 전용 수집 → 증거 묶음
                         ↓
                   원인 후보와 반례
                         ↓
                   수정안 검토
```

진단 과정에서 클러스터를 변경하지 않으면 수집 자체가 원래 상태를 흐리는 일을 줄일 수 있습니다. 다만 읽기 전용이라는 사실이 진단의 정확성을 보장하지는 않습니다. 수집한 정보의 범위와 시점도 결과에 포함해야 합니다.

## 모르는 상태를 결과로 남긴다

| 관측 | 말할 수 있는 것 | 추가 확인 |
|---|---|---|
| 이미지 이름과 태그 | 요청한 식별자 | 실제 태그 존재 여부 |
| 인증 실패 이벤트 | 해당 요청이 거부됨 | 자격 정보와 권한 범위 |
| 시간 초과 | 제한 시간 안에 완료되지 않음 | DNS·연결·레지스트리 상태 |

여러 원인이 같은 메시지를 만들 수 있으면 하나를 확정하지 않습니다. 증거가 부족하다는 상태를 명시하면 다음 수집 단계가 분명해집니다. 결과 화면에서도 확정된 사실과 제안된 조치를 다른 위계로 보여줍니다.

## 재현 가능한 입력으로 판단을 비교한다

검증 입력에는 관측 대상과 이벤트의 순서를 고정합니다. 기대 결과는 정답 문장 하나보다 필요한 근거가 포함됐는지, 관측하지 않은 사실을 단정하지 않는지, 읽기 전용 경계를 지켰는지로 나눕니다.

실제 운영 적용 전에는 오래된 이벤트, 권한 부족, 수집 중 대상 삭제를 다뤄야 합니다. 계약 테스트 통과와 실제 클러스터 연동 성공은 각각 확인할 항목입니다.
