## 응답을 잃어버린 클라이언트

주문 저장은 성공했지만 응답이 클라이언트에 도착하지 않은 상황을 가정합니다. 사용자는 다시 버튼을 누르고, 서버에는 같은 의도의 요청이 한 번 더 들어옵니다. 버튼을 잠시 비활성화하는 것만으로는 새로고침이나 네트워크 재시도를 막을 수 없습니다.

이 글에서 지킬 조건은 요청 횟수가 아니라 하나의 요청 의도에 하나의 처리 결과를 연결하는 것입니다. 화면의 편의와 저장소의 불변 조건을 나누어 설계합니다.

## 조회한 다음 저장하면 남는 틈

이미 처리한 키인지 조회하고, 없으면 주문을 저장하는 방식은 동시 요청 사이에 틈이 생깁니다. 두 요청이 모두 조회를 마친 뒤 같은 결론으로 저장할 수 있습니다. 중복 여부를 확인하는 작업과 결과를 소유하는 작업이 같은 원자적 경계 안에 있어야 합니다.

```sql
CREATE TABLE request_result (
  request_key text PRIMARY KEY,
  payload_hash text NOT NULL,
  order_id bigint NOT NULL
);
```

이 표는 설계의 일부입니다. 주문을 생성하는 트랜잭션과 키를 기록하는 트랜잭션을 분리하면 중간 실패를 다시 다뤄야 합니다. 실제 구현에서는 주문 변경과 결과 기록의 커밋 경계를 함께 정합니다.

## 같은 키가 같은 의도를 뜻하는가

| 도착한 요청 | 처리 방향 |
|---|---|
| 처음 보는 키 | 결과를 원자적으로 생성 |
| 같은 키와 같은 내용 | 앞서 저장한 결과 반환 |
| 같은 키와 다른 내용 | 충돌을 알리고 자동 덮어쓰기 금지 |
| 처리 중인 동일 키 | 완료 확인 또는 재시도 안내 |

외부 결제나 메시지 전송까지 데이터베이스 트랜잭션에 포함되는 것은 아닙니다. 저장 이후의 외부 동작은 별도의 전달 기록과 재시도 정책으로 다루어야 합니다. 데이터베이스 안에서 중복을 막았다는 이유로 전체 분산 흐름을 한 번만 실행했다고 말할 수 없습니다.

## 실패 지점으로 검증 범위를 나눈다

동일한 키로 동시에 요청하기, 커밋 직후 응답 끊기, 다른 내용으로 키 재사용하기를 각각 시험합니다. 응답 코드뿐 아니라 주문 행과 결과 행의 수를 함께 확인합니다.

예시 설계에는 키의 보관 기간과 외부 시스템 연동 정책이 남아 있습니다. 운영에 적용할 때는 클라이언트의 최대 재시도 기간보다 결과가 먼저 사라지지 않는지 확인해야 합니다.
